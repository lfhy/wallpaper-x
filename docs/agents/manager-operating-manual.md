# MyWallpaperX 多 Agent 管理手册

> 视角：我就是这个软件的负责人，我在管理机器人协作完成 MyWallpaperX
> 最后更新：2026-04-03

---

## 1. 我的角色

我不是在“让 AI 帮我写几段代码”，我是在管理一个会犯错、会越界、但执行速度很快的工程团队。

这个团队里的每个 Agent 都不是自由发挥的个体，而是我为了维护 `MyWallpaperX` 这套中型项目而划分出来的岗位。

我的目标不是让它们各自聪明，而是让它们：

- 各司其职
- 不越边界
- 不互相污染
- 在统一架构下稳定协作

我管理的不是“一个万能机器人”，而是一条受控流水线：

`Explorer -> Architect -> Protocol Steward / Module Agent -> Gatekeeper`

---

## 2. 我管理这套系统的基本原则

### 2.1 我先管边界，再管实现

在 `MyWallpaperX` 里，最危险的不是机器人写错一行代码，而是：

- 把模块之间直接连起来
- 把业务逻辑塞进 `Shell`
- 没搞清楚职责就去改公共层
- 在一个任务里顺手把别的模块也改了

所以我永远先问：

1. 这件事是谁的职责？
2. 这件事会不会破坏架构边界？
3. 这件事是不是已经触达公共协议层？

如果这三个问题没回答清楚，我不允许机器人直接写代码。

### 2.2 我把机器人当岗位，不当天才

我不要求每个 Agent 都理解整个项目。

我要求的是：

- `Explorer` 负责查清事实
- `Architect` 负责判责和拆任务
- `Protocol Steward` 负责公共层协作协议
- `Module Agent` 负责各自模块内部实现
- `Gatekeeper` 负责拒绝违规

谁越位，谁停下。

### 2.3 我允许快，但不允许乱

我接受最小变更、快速验证、边走边修正。

但我不接受：

- 跳过职责判断
- 直接按错误方案实现
- 因为“先做出来”而破坏架构
- 没审查就合入补丁

---

## 3. 我对 MyWallpaperX 当前架构的基本认知

为了管理机器人，我必须始终抓住这几个事实：

- `App/`、`Shell/`、`Shared/`、`docs/` 是公共层
- `Modules/*` 是模块层，默认不允许跨模块直接调用
- `Core/` 是敏感层，没有明确授权不应随便改
- 跨模块行为必须走 `Notification + Coordinator 中转`
- 菜单命令统一走 `MainWindowCoordinator`
- 菜单动态可用性统一走 `AppDelegate.validateMenuItem(_:)`
- 模块焦点统一走 `moduleDidBecomeActive + ModuleFocusable`
- 工具栏布局唯一主控是 `VideoLibraryToolbarController`

如果机器人给出的方案违背这些事实，我就认为它已经偏航。

## 4. 我如何给机器人派任务

### 4.1 我不会直接说“帮我改这个”

我会先要求它走流程。

我的标准开场是：

```text
先按 AGENTS 体系执行，不要直接改代码。
先做：
1. Explorer 扫描
2. Architect 判断职责与风险
3. 说明该由哪个 Agent 实施
4. 最后再决定是否动手

任务目标：
当前现象：
期望结果：
验收标准：
```

这样做的目的，是强制机器人先进入“管理模式”，而不是立刻进入“编码冲动模式”。

### 4.2 我会主动标明任务类型

我会先判断我给它的任务属于哪一类：

#### A. 模块内任务

例子：

- Steam 下载页搜索异常
- 图片库标签排序不对
- 视频库 QuickLook 行为错误

这类任务我要求：

- 先由 Architect 确认确实是模块内问题
- 然后只交给对应 Module Agent
- 不允许顺手动公共层

#### B. 公共协议任务

例子：

- 新增一个模块子页面
- 新增菜单能力并接入校验
- 新增路由、侧边栏、工具栏、焦点联动

这类任务我要求：

- 先由 Architect 判定“触达公共层”
- 再由 Protocol Steward 修改公共层
- 最后让对应 Module Agent 对接模块内部

#### C. 架构风险任务

例子：

- 让模块之间直接调 Service
- 想把业务逻辑塞到 `Shell`
- 想跳过 Notification 中转

这类任务我不允许直接实现。

我要求机器人先输出：

- `【越界风险】`
- 或 `【方案纠偏】`

先纠偏，再讨论。

## 5. 我如何判断该让谁工作

### 5.1 先问：是不是公共层问题

只要任务碰到这些内容，我就优先怀疑它属于 `Protocol Steward`：

- 路由
- Notification 定义
- 菜单分发
- 菜单校验
- 工具栏模式切换
- 焦点接管
- 架构文档同步

因为这些东西一旦写错，影响的不是一个功能，而是整个项目的协作秩序。

### 5.2 再问：是不是模块内部问题

如果问题只发生在某个模块内部，例如：

- 模块自己的列表
- 模块自己的搜索
- 模块自己的下载状态
- 模块自己的选择、多选、预览

那我就让对应 `Module Agent` 处理。

### 5.3 如果同时涉及两边，我拆成两段

这是我最重要的管理动作之一。

例如一个需求同时涉及：

- 公共层增加通知
- 模块层接收通知并更新 UI

我不会让一个 Agent 一次全做完。

我会拆成：

1. Protocol Steward 改公共协议
2. 对应 Module Agent 实现模块接入
3. Gatekeeper 审查二者是否一致

---

## 6. 我如何约束机器人不要乱做

### 6.1 我要求每次先做前置判断

我要它先回答：

- 这是不是你的职责范围？
- 这会不会违反项目规则？
- 这是不是你无权修改的层？

如果有问题，它必须先停下，而不是边做边解释。

### 6.2 我要求它主动纠正我

如果我提了一个技术上不合理的要求，我不希望机器人“听话”，我希望它“尽责”。

所以我要求它：

- 指出问题
- 说明为什么不合理
- 给出更合理方案

这不是唱反调，这是工程管理。

### 6.3 我只接受 diff patch，不接受模糊说明

凡是要改文件，我只接受 diff patch。

因为：

- patch 可审查
- patch 可追溯
- patch 易于最小变更
- patch 能让 Gatekeeper 真正工作

如果机器人只给我一段“建议改成这样”，那它还没进入受控协作状态。

## 7. 我如何用这套系统处理日常开发

### 7.1 做功能

我会这样发任务：

```text
按 AGENTS 流程处理。
先不要改代码，先给我：
1. Explorer Report
2. Architect 决策
3. 应由哪个 Agent 实施

任务目标：
当前行为：
目标行为：
验收标准：
```

如果 Architect 结论合理，我再让它继续输出 diff patch。

### 7.2 做排障

我会这样发任务：

```text
按 AGENTS 流程排查，不要先修。
先由 Explorer 输出：
- 涉及文件
- 涉及模块
- 涉及通知 / 路由 / 菜单 / 焦点触点
- 可能违规点
- 初步责任归属
```

这样我先拿到上下文，再决定怎么修。

### 7.3 做重构

我会这样发任务：

```text
这是架构敏感改动。
先由 Architect 判断：
- 是否触达公共层
- 是否需要 Protocol Steward
- 哪些内容禁止模块 Agent 顺手修改
确认后再拆分补丁。
```

### 7.4 做审查

我会这样发任务：

```text
进入 Gatekeeper 审查模式。
重点检查：
- 是否跨模块直连
- 是否绕过 Notification
- 是否误改 Core / Shared
- 是否漏了 framework-architecture-memo.md
- 是否漏了菜单 / 路由 / 焦点一致性
```

## 8. 我如何理解“稳定协作”而不是“AI 各自行动”

稳定协作不是让每个 Agent 都很聪明。

稳定协作是：

- `Explorer` 不抢实现
- `Architect` 不跳过扫描
- `Module Agent` 不越过自己目录
- `Protocol Steward` 不替模块写业务
- `Gatekeeper` 不装宽松

只要有人越位，短期也许更快，但长期一定会让项目失控。

我管理这套系统时，宁可多一次职责判断，也不愿意多一次跨层污染。

---

## 9. 我对“我自己”的要求

如果我是这个软件的负责人，那我自己也必须守规矩。

我不能因为着急，就要求机器人：

- 直接跳过扫描
- 不做职责判断
- 先改了再说
- 暂时绕过架构
- 让某个模块直接连另一个模块

因为我一旦这样做，机器人只会学会一件事：

规则是可以在压力下失效的。

而一旦规则在压力下失效，这套多 Agent 体系就会退化成“几个机器人乱改同一个项目”。

## 10. 我的标准工作口令

下面这些，是我以后会反复使用的标准口令。

### 10.1 任务启动口令

```text
先按 AGENTS 流程执行，不要直接改代码。
先给我 Explorer Report 和 Architect 决策。
```

### 10.2 公共层任务口令

```text
这是公共协议接入任务。
先由 Architect 判断，再转 Protocol Steward。
模块 Agent 不得直接扩散修改公共层。
```

### 10.3 模块任务口令

```text
如果这是模块内问题，只允许对应 Module Agent 改本模块目录。
不要顺手改 App / Shell / Shared / docs。
```

### 10.4 风险拦截口令

```text
如果存在越界、错误设计或无权限修改，禁止执行。
先输出【越界风险】或【方案纠偏】。
```

### 10.5 审查口令

```text
进入 Gatekeeper 审查模式。
先判定是否违反架构红线，再决定是否放行。
```

---

## 11. 结论

我不是在用 AI 替我写代码。

我是在用一套有岗位、有边界、有协议、有审查的协作系统，来管理 `MyWallpaperX` 的持续演进。

这套系统真正保护我的，不是“它会写 Swift”，而是：

- 它会先判断职责
- 它会在越界时停下
- 它会在我说错时纠偏
- 它会把跨模块协作收束到统一协议
- 它会把补丁交给 Gatekeeper 审查

只有这样，机器人才能长期成为我的工程能力放大器，而不是不稳定的风险来源。
